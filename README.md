# PatientTriage.ai — Working AI Decision-Support Prototype

> ⚠️ **This prototype is an AI decision-support system for research/demo purposes
> and is not a medical device or a substitute for clinical judgment.**
> No real patient data is used anywhere. No performance number in this repo
> should be read as a clinical-validation claim.

## What this actually is

A functioning, runnable prototype (not a mockup) that implements the
architecture in the problem statement: two independently-trained ML
models, a deterministic safety layer, an uncertainty engine, a
verification/disagreement engine, mandatory clinician override,
append-only audit logging, waiting-room deterioration monitoring, and a
3× surge simulation — wired together behind a Streamlit dashboard.

## 1. Architecture

```
PATIENT INPUT
   |
   v
DATA QUALITY / MISSING-DATA LAYER  (preprocessing.py)
   |
   +-------------------+
   |                    |
   v                    v
MODEL 1              MODEL 2
(XGBoost)            (MLP neural net, independent features)
   |                    |
   +--------+-----------+
            v
     VERIFICATION ENGINE (verification.py)
      + SAFETY LAYER (safety_rules.py, never lets ML under-escalate)
      + UNCERTAINTY ENGINE (uncertainty.py)
            |
   +--------+---------+----------------+
   v                  v                v
 AGREE            DISAGREE         INSUFFICIENT DATA
   |                  |                |
   +--------+---------+----------------+
            v
     CLINICIAN OVERRIDE (app.py Accept/Override UI)
            v
     AUDIT LOG (audit.py, JSONL, append-only)
            v
     WAITING-ROOM MONITORING (monitoring.py) --> RE-TRIAGE
```

## 2. Dataset — read this before trusting any number in this repo

**No real clinical dataset (e.g. MIMIC-IV-ED) is used.** MIMIC-IV-ED
requires credentialed PhysioNet access that is not available in this
sandboxed environment (only package registries are network-reachable
here). Using a real ED dataset would also require IRB-level data-use
agreements inappropriate for a hackathon sandbox.

Instead, `src/data_generation.py` produces a **clearly labeled synthetic
dataset** (3,000 patients for training, plus a 22-patient fixed
demonstration cohort in `demo_patients.py`), generated by a
**documented, deterministic rule-based labeling function**
(`assign_label_and_reason`) loosely informed by the *publicly described
logic* of the Emergency Severity Index (danger signs → resource need →
vital-sign severity). This function is a simplification written for this
prototype — it is **not** a reproduction of ESI training materials, not
clinically validated, and not reviewed by a clinician.

**Consequence:** every accuracy/F1/recall number in `evaluate.py`'s
output measures *how well each model recovers this synthetic labeling
rule* — not real-world clinical accuracy. Treat all such numbers as a
methodology demonstration only.

`src/data_generation.py::load_real_dataset()` is a stub showing where a
real, properly licensed dataset would plug in with minimal changes to
`preprocessing.py`.

Dataset composition includes normal, critical, ambiguous, pediatric,
geriatric, zero-history, missing-vitals, missing-history, and
vital/symptom-mismatch cases (both directions), generated with a fixed
NumPy `Generator` seed (`RANDOM_SEED = 42`) for reproducibility.

**Matches the brief's stated reference parameter.** The Round 2 brief
states: "assume mixed data availability — roughly half of arriving
patients have some prior health record on file, half do not." The
generator now assigns `has_history_info` via a ~50/50 coin flip across
the general patient population (independent of the explicitly-forced
`zero_history` / `missing_history` demo categories, which exist to
guarantee those specific cases always appear in every generated batch).
Verified on a fresh 3,000-patient run: **51.3%** of generated patients
have a prior record on file — matching the brief's assumption.

## 3. Features

- **Structured:** age, HR, RR, SBP, DBP, SpO2, temperature, pain score
- **Missingness indicators:** `<field>_missing` for every vital, plus
  `has_history_info` (explicitly distinguishes "confirmed no history"
  from "history not available" — Section 9 of the spec)
- **Derived:** shock index (HR/SBP), pulse pressure, missing-field count,
  pediatric/geriatric flags
- **Text:** chief complaint + symptoms + history, vectorized two
  different ways (see Model 2 below)

## 4. Model 1 — primary triage classifier (`src/model1.py`)

XGBoost multiclass classifier (`multi:softprob`) over structured
features + word-level TF-IDF (1-2 grams) of the clinical text. Falls
back to RandomForest automatically if `xgboost` is unavailable. Outputs
per-class probabilities, a confidence score, and (via
`feature_importances_`) the top contributing structured features.

## 5. Model 2 — independent verification model (`src/model2.py`), selected on evidence via `model2_selection.py`

**Deliberately not "Model 1 run twice."** It differs in three ways:
1. **Different text representation:** character n-gram (3-5) TF-IDF
   instead of word n-grams.
2. **Different scaling:** MinMax instead of Standard scaling.
3. **Different algorithm:** a feed-forward neural network
   (`sklearn.neural_network.MLPClassifier`, two hidden layers) instead of
   gradient-boosted trees.

**Both models receive the same complete evidence.** Model 1 and Model 2
are built from the same structured numeric feature matrix and the same
combined text corpus (chief complaint + symptoms + history) — only the
*representation* of that text differs (word n-grams vs. char n-grams),
never the underlying information. Neither model ever sees a subset of
what the other model sees.

**Model 2's architecture is evidence-based, not assumed.**
`model2_selection.py` benchmarks three candidates — all built on
identical evidence — and picks a winner by measured performance rather
than by design intuition:

| Candidate | Accuracy | Macro-F1 | Critical recall | Under-triage | Brier score |
|---|---|---|---|---|---|
| A. Logistic Regression | 0.668 | 0.673 | 0.808 | 0.180 | 0.453 |
| B. Linear SVM (calibrated) | 0.682 | 0.691 | 0.788 | 0.175 | 0.435 |
| **C. MLP (2-layer)** | **0.725** | **0.727** | **0.833** | **0.165** | **0.383** |

Selection rule (documented, not hidden): highest critical-class (ESI1-2)
recall first, macro-F1 as tiebreaker — under-triage risk is weighted
above raw accuracy, consistent with the safety-first framing throughout
this project. MLP wins on every metric measured, so it's kept as Model 2
— now for a measured reason instead of an assumed one. Full numbers are
written to `models/model2_candidate_comparison.json` each time the
script runs.

A full pretrained clinical transformer (e.g. a BioClinicalBERT-style
model) was considered but is **not practical here**: this sandbox's
network allowlist covers only package registries (PyPI/npm/crates.io/
GitHub release assets) — verified to have no route to huggingface.co or
any model-hub download endpoint, so pulling multi-GB pretrained weights
is not physically possible in this environment, not merely
inconvenient. The `Model2` class and `TriagePipeline` interface are kept
swappable so a real clinical transformer could be substituted later
without touching Model 1, the safety layer, or the verification engine.

## 6. Safety layer (`src/safety_rules.py`, age-aware via `src/age_bands.py`)

Deterministic, auditable rules (e.g. low SpO2, low SBP, extreme
respiratory rate, a short list of danger-sign keywords). If a rule
fires, it can only ever push the final ESI **more urgent**, never less —
the ML prediction can never silently downgrade a patient below a
triggered safety rule. These are explicitly labeled prototype heuristics,
not a reproduction of any specific clinical guideline.

**Age-aware thresholds.** The brief specifically warns that "solutions
that apply a single adult-calibrated scoring model across all age
groups introduce silent safety risk." `src/age_bands.py` is the single
shared source of truth (used by `safety_rules.py`, `preprocessing.py`,
and `data_generation.py`) defining separate critical/warning cutoffs for
pediatric, adult, and geriatric patients — e.g. a heart rate of 150 bpm
is a `SAFETY_HR_EXTREME` flag for an adult but unremarkable for a
4-year-old; a temperature of 38.3°C is flagged as a high fever for a
geriatric patient (who may not mount a strong fever response even when
seriously ill) but not for an adult. This was verified directly:

```
Pediatric, HR=150, RR=30  -> no safety flags (normal range for a child)
Geriatric, SBP=98, SpO2=93, Temp=38.5 -> SAFETY_SBP_LOW, SAFETY_TEMP_HIGH
Adult, same vitals                    -> only SAFETY_SPO2_LOW
```

Same numbers, different age, different safety outcome — which is
exactly the failure mode the brief calls out.

## 7. Uncertainty engine (`src/uncertainty.py`)

Combines four signals rather than just "max probability":
top-2 probability margin, normalized entropy, a missing-data score, and
Model 1/Model 2 disagreement (weighted highest). Produces LOW / MODERATE
/ HIGH with a plain-language reason list. A close top-2 (e.g. ESI2=0.48
vs ESI3=0.45) is flagged HIGH even though technically "confident."

## 8. Verification engine (`src/verification.py`)

- **AGREEMENT** — both models pick the same ESI.
- **DISAGREEMENT** — models differ; the system does **not** auto-pick a
  winner. It surfaces both predictions, flags for mandatory nurse
  review, and provisionally shows the more-urgent of the two as a
  conservative placeholder.
- **INSUFFICIENT_DATA** — triggered even when models agree, if too much
  intake data is missing.

Safety-layer flags and HIGH uncertainty both force
`nurse_review_required = True` regardless of model agreement.

**Agreement tiers.** Plain "disagreement" isn't one thing — a 1-level
gap (ESI 2 vs. 3) is a very different signal from a 2+ level gap
(ESI 2 vs. 5). `classify_agreement_tier()` distinguishes:
`AGREE` (identical prediction), `DISAGREE` (1-level gap), and
`MAJOR_DISAGREE` (2+ level gap, always forces nurse review regardless of
any other signal). Every model output (both Model 1 and Model 2) also
now carries `model_version`, `preprocessing_version`, `max_probability`,
and `top2_margin` — not just the top prediction — so the audit trail can
always reconstruct exactly what each model produced and under which
pipeline version.

## 8a. Crash-safe model saving (`src/atomic_save.py`)

Model files are saved via an atomic write (write to a temp file, then
`os.replace()` into place) instead of writing directly to the target
path. This closes a real failure mode: if training is interrupted
mid-save (browser tab closed during first-run auto-training, terminal
killed, machine sleeps), a direct write can leave a truncated, corrupted
`.joblib` file sitting at the expected path — which then fails to load
on the next launch with an opaque unpickling error. With the atomic
write, `os.replace()` is a single filesystem operation: it either fully
completes or doesn't happen at all, so the file at the real path is
either the previous good version or the new one — never something
in-between. Verified directly: a forced mid-save crash left the
original file byte-for-byte unchanged with no leftover temp file.

## 8e. Automatic dept movement, Modify ESI, Vertical Care timer, and slug-based routing

A fourth round of fixes on top of the pathway/bed-release system above:

**1. Override/accept always auto-moves the patient (no confirm step).**
`apply_accept()` and `apply_override()` now call
`auto_assign_pathway_from_esi()` internally, every time — a clinician
decision (accept counts as one) is immediately treated as final and the
patient moves to the matching dept without a separate "confirm move"
click. This supersedes the earlier Main-ED bed-release workflow's
confirm button for the normal reassessment path (verified via updated
tests); the freed-bed-and-next-candidate surfacing logic moved from the
Waiting Room into the Accept/Override handlers themselves, right where
the move now actually happens.

**2. "Modify ESI" — a separate quick clinical-judgment path
(`apply_manual_esi_edit()`).** Each patient row now has two buttons:
`[REASSESS PATIENT]` (the existing full model-rerun flow) and
`[✏️ Modify ESI]`, which lets a nurse type a new ESI directly with a
reason, no model rerun. This is intentionally a *different* function
from `apply_override()` — it's tagged `manual_esi_edit=True` for the
audit trail and, critically, does **not** auto-move the pathway by
itself. The caller decides based on shift state:
- **Surge active:** the pathway moves immediately on save, no extra
  click (`auto_assign_pathway_from_esi()` called right after saving).
- **Quiet shift:** the ESI is saved but the patient stays shown in
  their current dept until the nurse explicitly clicks
  `[➡️ SEND TO <dept>]`, which appears automatically whenever the saved
  ESI's guideline pathway no longer matches where the patient is
  currently shown.
Verified both branches directly end-to-end in a standalone script.

**3. Dedicated Vertical Care 30-minute timer, ESI-3 only.**
`check_vertical_care_timer()` is a separate, independently-resettable
timer from the general ED wait-time tracking — `set_pathway()` stamps
`vertical_care_timer_start` only on a genuine transition *into*
Waiting/Vertical Care, and the timer is only ever `applicable` for a
patient whose *current pathway is Vertical Care AND current final ESI
is exactly 3* — verified that an ESI-1/2 patient who overflows into
Vertical Care during surge does **not** get this timer. A `🔄 Reset
Timer` button lets the nurse restart it at her own judgment,
independent of the rest of the patient's state.

**4. Slug-based tab routing (`?page=new_patient` etc.).** The sidebar
navigation is now driven by `st.query_params` in addition to
`st.session_state["nav_page"]` — every page has a stable slug
(`dashboard`, `new_patient`, `waiting_room`, `surge_simulation`,
`audit_log`). `navigate_to(page_name)` is the single function every
button (Waiting Room's `[REASSESS PATIENT]`, etc.) calls to switch tabs
reliably, and manual sidebar clicks keep the URL in sync too — so the
current tab is bookmarkable/shareable and survives a refresh.

**Tests:** `tests/test_realtime_and_pathways.py` was extended with 8
more assertions (34 total in that file) covering auto-move-on-accept,
Modify ESI's quiet/surge branching, and the Vertical Care timer's
ESI-3-only scoping and reset behavior. All passing.

## 8d. Real-time Waiting Room clock, three care pathways, and surge Main-ED bed release

A further round of changes to the Waiting Room, built on the state
model above:

**Real-time timer, no manual advancement (Part 1).** `wait_minutes` (a
manually-incremented counter) is gone entirely. Every patient record
now stores `arrival_timestamp` — a real `time.time()` epoch value set
once at creation and never touched again, not even by a reassessment.
Waiting time is always `time.time() - arrival_timestamp`
(`patient_state.elapsed_seconds()` / `format_elapsed()`), so it's
correct after a page navigation, a browser refresh, or a UI restart —
there's no counter to desync. The Waiting Room uses
`streamlit-autorefresh` to re-render every second so the on-screen
timers visibly tick without the nurse clicking anything. The old "+30
minutes" simulation button is removed from the real Waiting Room
entirely — real and simulated time are now fully separated, exactly as
the spec requires; the Surge Simulation page's own synthetic cohort is
untouched and still uses its own simulated clock.

**Three care pathways (Parts 3-5, 12).** `patient_state.suggest_pathway(esi)`
returns a *guideline* (ESI 1-2 → Main ED, ESI 3 → Waiting/Vertical,
ESI 4-5 → Fast/Normal) — never an automatic assignment. The Waiting
Room is now three sections, each with its own patient list, live
timers, and a `[REASSESS PATIENT]` (or `[UPDATE / REASSESS ESI]` in
Main ED) button. A nurse can freely move a patient's pathway
independent of ESI, and that choice persists through later
reassessments rather than being silently recomputed.

**Surge Main-ED bed release (Parts 6-11, 23).** Main ED bed occupancy
is computed *live* from actual current pathway assignments
(`main_ed_bed_state()`) rather than a manually incremented/decremented
counter — this avoids an entire class of drift bugs where a stored
count goes stale. A Main ED patient becomes bed-release-eligible
(`bed_release_eligible()`) **only** when a genuine reassessment
produces a clinician-final ESI ≥ 3 — verified directly that neither a
long wait time nor surge pressure alone can trigger eligibility. When
eligible, the Waiting Room shows a suggestion banner and a
`[CONFIRM MOVE]` button — nothing moves without an explicit click.
After a bed frees, `find_next_main_ed_candidate()` surfaces (never
auto-assigns) the lowest-ESI, longest-waiting eligible patient
currently outside Main ED. **Verified against the spec's own Part 17
worked example**: 3 Main ED beds, all 3 occupied by ESI-2 patients;
reassessing one to ESI 3 correctly dropped occupancy to 2/3 with 1 bed
available — reproduced exactly via a standalone script.

**Tests:** `tests/test_realtime_and_pathways.py` — 26 assertions
covering the real-time timer, pathway guideline behavior, live bed-state
computation, and the bed-release eligibility rule (including the
explicit "surge/wait-time alone is never sufficient" safety check from
spec Part 11). All passing.

## 8c. Reassessment workflow, real explainability, and override-controlled Waiting Room

Three targeted changes to the existing UI/data model, built on top of everything above:

**1. Waiting Room → Reassessment is now directly actionable.** The
underlying state model (`src/patient_state.py`) treats every patient as
a `patient_id` + `encounter_id` with a list of `assessments` — never
overwritten, only appended to. Clicking **[REASSESS PATIENT]** in the
Waiting Room stores the previous assessment's full input snapshot,
switches to the New Patient tab, and pre-fills every field (vitals,
complaint, symptoms, history) — the nurse edits only what's changed and
resubmits. This creates a NEW assessment linked via `previous_assessment_id`,
never a new patient. Verified end-to-end: a patient assessed at ESI 4,
accepted, then reassessed with deteriorating vitals correctly escalated
to ESI 1, with both assessments intact in the audit timeline afterward.

**2. Explainability is now built on real SHAP attribution, not just
feature-importance names.** `src/explainability.py`:
- **Model 1 (XGBoost):** genuine `shap.TreeExplainer` attribution for
  the predicted class, translated into sentences using the patient's
  actual values (e.g. *"Oxygen saturation (SpO2 90%) increased the
  likelihood of this ESI 2 assessment"*) — never raw feature names like
  `shock_index` or `sbp_missing`. Uninformative stopword tokens are
  filtered from the *display* (the underlying SHAP values are
  unchanged) since a sparse word-TFIDF vocabulary can otherwise surface
  meaningless high-attribution tokens like "of" or "no".
- **Model 2 (MLP + char-ngram TF-IDF):** true per-feature attribution
  isn't human-readable for this architecture (a SHAP value on the
  character sequence "hest p" means nothing to a nurse). Per the
  instruction to state the limitation rather than fabricate, Model 2's
  explanation instead lists curated clinically-relevant phrases
  confirmed present in the patient's own narrative — real evidence the
  model actually received, explicitly labeled as evidence-presence, not
  attribution.
- **Agreement case:** shows both models' real contributing factors and
  states they independently reached the same ESI.
- **Disagreement case:** shows both sides separately, and — critically —
  when no reliable causal reason for the disagreement can be
  established (the normal case, since the two models use different
  algorithms and representations), it says so explicitly rather than
  inventing a mechanism. Verified in `tests/test_new_features.py` that
  the disagreement explanation never contains a fabricated claim like
  "the NLP model ignored X."
- **History evidence:** if the retrieved history text contains an
  `[ACTIVE HISTORY]` section, those findings are shown with a
  combination-only framing ("contributed in combination with the
  current presentation"), never a standalone causal claim.

**3. Clinician override now controls what the Waiting Room displays.**
Every assessment stores `ai_recommended_esi` and `clinician_final_esi`
as two separate, permanent fields — an override never overwrites the
original AI recommendation. The single rule used everywhere
(`patient_state.get_displayed_esi()`): show `clinician_final_esi` if a
decision has been made, otherwise fall back to `ai_recommended_esi`.
Verified: AI recommends ESI 3, nurse overrides to ESI 2 — the Waiting
Room and Dashboard now show ESI 2 with a "Clinician Override" indicator,
while ESI 3 remains permanently stored and auditable. A later
reassessment adds a new entry without ever deleting the override
history — `assessment_timeline()` exposes the full sequence.

**Tests:** `tests/test_new_features.py` — 34 assertions across all six
required test scenarios (waiting-time reassessment, history
preservation, agreement explanation, disagreement explanation with
no-fabrication check, override display, and reassessment-after-override
audit preservation). All passing; run with `python3 tests/test_new_features.py`.

## 8b. Patient database & automatic history retrieval (`database/`, `src/history_context.py`)

Spec Sections 7-18: Patient ID is now the first step of the New Patient
workflow, not an afterthought.

- **`database/schema.py`** — SQLite schema with `patients`, `encounters`,
  `diagnoses`, `vitals`, `medications`, `allergies`, and `clinical_notes`
  tables. History is stored as individual timestamped rows, never as one
  giant text blob, and `event_date` (when something happened) is tracked
  separately from `recorded_at` (when it was documented).
- **`database/repository.py`** — the only module allowed to run SQL. It
  classifies every lookup into exactly one of three states, verified to
  behave distinctly:
  - **`FOUND`** — patient exists with clinical records; full history
    retrieved automatically.
  - **`NO_RECORD`** — patient exists but genuinely has no records (a
    confirmed absence, not a failure).
  - **`UNAVAILABLE`** — retrieval failed (simulated via the reserved ID
    `SIMULATE-DB-OUTAGE`); the system explicitly does NOT treat this the
    same as "no history."
- **`database/seed.py`** — populates 5 synthetic demo patients with
  multi-encounter histories, covering: relevant history (prior MI +
  recurring cardiac complaints), unrelated history (old kidney stone),
  recent chronic condition (pediatric asthma), old history (10-year-old
  CAD diagnosis), and a "frequent flyer" pattern (5 ED visits with
  worsening severity).
- **`src/history_context.py`** — turns a retrieved history bundle into
  (a) a clinical-language text block in the spec's Section 17 format,
  which is appended to the SAME text corpus both models already read —
  so history reaches both models through the existing "same complete
  evidence, different representation" pathway with no pipeline changes
  needed — and (b) structured temporal summary features
  (`days_since_last_encounter`, `active_diagnosis_count`, previous
  vitals for delta computation) that are computed and available now but
  not yet wired into the trained numeric feature vector — see the
  Deferred note in that file and Section 13 below for what that would
  take.

Verified live end-to-end: looking up `PT-1001` (67-year-old, prior MI,
recurring cardiac complaints) and presenting with severe chest pain +
abnormal vitals today correctly produced **ESI 1 (CRITICAL)** via the
safety layer, with the two models genuinely disagreeing (2 vs. 1) —
exactly the kind of case the spec's own worked example describes.

In the app: the New Patient page now opens with a Patient ID search box.
Search retrieves history automatically and pre-fills the history field
(editable, never forced) — a nurse never has to manually retype history
that's already on file. Try `PT-1001`, `PT-1002`, `PT-1003`, `PT-1004`,
`PT-1005` (seeded), any made-up ID (NO_RECORD), or
`SIMULATE-DB-OUTAGE` (UNAVAILABLE).

## 9. Clinician override (`app.py` → New Patient page)

Accept / Override buttons after every assessment. An override requires
a typed reason and is logged with patient ID, timestamp, both model
outputs, AI recommendation, clinician decision, reason, model version,
input completeness, and safety flags (`src/audit.py`).

## 10. Waiting-room monitoring (`src/monitoring.py`)

Reassessment is triggered by **two independent mechanisms**, matching
the brief's explicit requirement to "trigger re-assessment if wait time
exceeds safe thresholds for their severity level **or** if vitals are
re-recorded as worsening" (both, not just one):

1. **Vitals-based** — explicit delta thresholds (e.g. SpO2 drop ≥4 pts,
   HR rise ≥20 bpm) between a patient's initial and current vitals.
2. **Wait-time-based** (`check_wait_time_breach`) — a patient is flagged
   purely for having waited longer than a safe ceiling for their current
   ESI level, even if nobody has re-taken their vitals at all. Ceilings
   used (illustrative, not a clinical standard): ESI 1 → 0 min (should
   never be "waiting"), ESI 2 → 10 min, ESI 3 → 30 min, ESI 4 → 60 min,
   ESI 5 → 120 min.

`assess_waiting_patient()` combines both checks into one status:
`WAITING` (neither triggered), `REASSESSMENT_REQUIRED` (one triggered),
or `ESCALATED` (both triggered simultaneously). Verified directly: an
ESI-2 patient who has waited 15 minutes with **completely unchanged
vitals** is still flagged (`wait_time_breached=True`), while an ESI-4
patient at the same 15-minute mark is not — because 15 minutes is safe
for ESI-4 but not for ESI-2. The Waiting Room page in `app.py` lets you
advance time by any amount and shows both flags separately so a nurse
can see exactly which trigger fired.

## 11. Surge simulation (`app.py` → Surge Simulation page, `src/surge_simulation.py`)

This is a **real discrete-event queueing simulation**, not a static
multiplier. It models:
- Patient arrivals over a simulated 8-hour shift via a Poisson process,
  with an average rate derived from the target daily volume (100/day
  normal vs. 300/day surge).
- A **fixed number of treatment slots** (nurses/bays, configurable in
  the UI) — identical in both the normal and surge run, which is the
  entire point: surge stress-tests a fixed-capacity system, it doesn't
  add more capacity.
- Priority-based service: the highest-urgency (lowest ESI) waiting
  patient is pulled first whenever a slot frees up, not simple
  first-come-first-served.
- Each patient's simulated treatment duration scales with their ESI
  (critical patients occupy a slot longer) — an illustrative assumption.
- **Safety-wait-breach counting**: reuses the exact same
  `MAX_SAFE_WAIT_MINUTES` ceilings from Section 10 to count how many
  simulated patients would have breached their safe-wait ceiling before
  being seen, broken down by ESI level. This is the direct, quantified
  link between "more volume" and "more safety risk" — the actual
  observed result from a real run with 5 fixed treatment slots:

  ```
  Normal (100/day):  0 safety-wait breaches
  Surge  (300/day):  64-80 safety-wait breaches, including several
                      among CRITICAL (ESI 1-2) patients
  ```

  The safety RULES and ESI thresholds are byte-for-byte identical
  between the two runs — what changes is purely the queueing outcome of
  tripling arrivals against fixed capacity, which is exactly the
  distinction the brief asks prototypes to demonstrate explicitly.

This is a substantial upgrade over a proportional-scaling estimate, but
is still a simplified model — no staffing schedules, bed-turnover
logic, walkouts, or multi-resource contention (labs, imaging) are
simulated. The page also still runs the original ML-batch comparison
(model outputs at 1× vs 3× volume) alongside the queueing simulation.

## 12. Regulatory jurisdiction & patient data protection

Per the brief's explicit request to state an assumed jurisdiction: this
prototype assumes a **US deployment governed by HIPAA**. Full design
notes — what that implies for audit trail design, retention policy, and
what an override must legally capture, plus what is and isn't actually
implemented in this prototype vs. what a real deployment would need
(access control, encryption, BAAs, consent model, breach notification)
— are in **[`PRIVACY_DESIGN.md`](PRIVACY_DESIGN.md)**. Short version:
the audit trail already captures the fields a compliance review would
want (timestamp, both models' outputs, clinician decision + reason,
model version, input completeness, safety flags); what's genuinely
missing for production is encryption, role-based access control, and a
retention/purge policy — none of which make sense to fully build for a
prototype running only on synthetic data with no real users, but all of
which are named explicitly rather than silently skipped.

A few items the brief raises as design considerations rather than
prototype-build requirements — addressed here in the write-up rather
than in code, per the brief's own framing ("you are not expected to
address every point listed"):

- **Hospital-scale variability** (100 vs. 500+ visits/day, different
  specialty mixes): the pipeline itself doesn't hard-code any volume
  assumption — `n_servers` in the surge simulation and the underlying
  ESI/safety logic are volume-independent by construction. Scaling to a
  larger hospital is primarily a configuration change (more treatment
  slots, more concurrent sessions), not a redesign. A smaller rural ED
  would likely want a lighter-weight deployment (e.g. skip Model 2's
  neural net and rely on Model 1 + the safety layer alone) given lower
  patient volume for retraining and lower tolerance for infrastructure
  complexity — worth prototyping as a "lite mode" in a future iteration.
- **EHR/bed-management/roster integration**: not attempted here — this
  prototype has no interface to any external system. In a real rollout,
  the natural integration point is at intake (pull existing history
  from the EHR to populate `has_history_info` and prior vitals
  automatically rather than manual entry) and at the audit-log layer
  (writing decisions back into the hospital's clinical record system
  instead of a standalone JSONL file).
- **Adoption / change management**: not addressed in code. The
  single biggest risk to real adoption is a fatigued nurse ignoring or
  routing around the tool. A credible rollout would start in
  **shadow mode** (the AI runs and logs recommendations silently
  alongside normal nurse-led triage, with no visible action for several
  weeks) so accuracy and override patterns can be reviewed before the
  tool is trusted to actively influence a queue, plus a visible feedback
  loop so nurses see their overrides taken seriously rather than logged
  and ignored.

```bash
pip install -r requirements.txt

# 1. Train both models on the synthetic dataset
python3 train.py

# 2. (Optional) Seed the patient history database with demo patients
#    (PT-1001 through PT-1005) for the Patient ID search workflow

#    Regression vs. calibrated Linear SVM vs. MLP) — confirms the MLP

# 4. Full evaluation (accuracy, F1, confusion matrix, under-triage,
#    critical-class recall) written to models/evaluation_report.json
python3 evaluate.py

# 4b. Run the reassessment/explainability/override test suite
python3 tests/test_new_features.py

# 4c. Run the real-time timer / care pathway / surge bed-release test suite
python3 tests/test_realtime_and_pathways.py

# 5. Run the 22-patient demonstration set end-to-end (safety triggers,

streamlit run app.py
```

## 15. Evaluation — what was actually measured (see `models/evaluation_report.json` after running)

On the held-out synthetic test set (600 patients, stratified split, after
the data-generation and age-band updates above):
- Model 1 (XGBoost): **0.857 accuracy / 0.858 macro-F1**, critical-class
  (ESI1-2) recall **0.943**, under-triage rate **7.0%** (42 patients).
- Model 2 (MLP): **0.725 accuracy / 0.727 macro-F1**, critical-class
  recall **0.833**, under-triage rate **16.5%** (99 patients).
- Model1/Model2 disagreement rate on the test set: **23.8%**.

These numbers are **real outputs of real training runs on synthetic
data** — not fabricated — but again measure recovery of a synthetic
labeling rule, not clinical performance. `evaluate.py` explicitly
reports **under-triage** (predicting less urgent than the synthetic
truth) and **critical-class recall** front-and-center per the spec,
because under-triage is the more dangerous failure mode.

## 16. Limitations (read before treating this as more than a demo)

- Synthetic data only; no real ED outcomes; labeling rule is a
  simplification, not a validated instrument.
- Model 2 is a lightweight MLP, not a pretrained clinical language
  model — a real deployment would likely use a proper clinical
  transformer with real data.
- Safety-layer thresholds, including the age-band cutoffs in
  `age_bands.py` and the wait-time ceilings in `monitoring.py`, are
  illustrative prototype constants, not sourced from a specific
  clinical guideline or published pediatric ESI standard.
- No demographic/fairness audit has been performed.
- Not tested against real-world ED throughput, staffing constraints, or
  EHR integration (see Section 13 — Roadmap for how this would be
  approached).
- The surge/queueing simulation is a simplified single-resource-type
  model — it does not account for bed turnover, lab/imaging
  contention, or staff shift changes.
- No access control, encryption, or formal retention policy is
  implemented (see `PRIVACY_DESIGN.md` for what's assumed vs. missing).
- This system has not undergone any regulatory review and must never be
  used on real patients.
